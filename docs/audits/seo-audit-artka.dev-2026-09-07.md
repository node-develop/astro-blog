## Правила публикации через API

Автоматизация доставки уже работает. Автоматизация выдумывания опыта не должна стать источником новых ошибок.

Перед публикацией агент обязан приложить первичные источники к изменчивым фактам, отличить наблюдение от предложения, проверить код или назвать его псевдокодом, сохранить исходную дату публикации и обновить обе языковые версии. Личный опыт, проценты, benchmark и цитата требуют доказательства. Ссылка из X — повод исследовать тему, а не достаточный источник всех утверждений.

Это редакционный процесс, пока не технический блокировщик Content API. JSON-схема не способна подтвердить правдивость статьи. Дополнительные правила находятся в `docs/editorial-quality.md`.

### Недели 2–4

Выпускать примерно один доказательный материал в неделю, если готово содержание. Не увеличивать частоту за счёт пересказов.

Три тематические линии, основанные на существующем сайте, а не выдуманной частотности:

- **Надёжность coding agents:** ошибка инструмента → минимальный reproducer → исправление → тест.
- **Публикация на Astro:** идемпотентная подача статьи, изображения и ошибки сборки на примере собственного Content API.
- **Контент и индексирование:** реальные URL до/после, поведение canonical и редиректов, наблюдения GSC с датами.

Для каждого материала: один вопрос читателя, собственный артефакт, первичные источники, понятное ограничение, ссылка из соответствующего курса и на соседний полезный разбор. Поддерживать существующий URL при обновлении той же темы. Публиковать RU/EN только после проверки обеих версий.

Внутренний Pagefind сейчас индексирует только 10 статей RU/EN; уроки доступны через оглавление. Расширение поиска на уроки — отдельное улучшение навигации, а не установленная причина решения Google.

### Дни 30–60

Сравнить последовательные 28-дневные периоды в GSC: показы и клики **контентных страниц**, количество текущих canonical в индексе, последние даты обхода, появившиеся реальные запросы. Отдельно учитывать главную и брендовые запросы, если данных уже достаточно.

Для страниц с показами и слабым ответом на запрос — улучшить содержание. Для обнаруженных без обхода — проверить внутренние ссылки и технический доступ. Для crawled-not-indexed после свежего успешного обхода — сравнить уникальность задачи, доказательства и соответствие поисковому намерению. Не менять всё одновременно без фиксации причины.

### Дни 60–90

Развивать темы, у которых появились содержательные показы и обратная связь. Слабые дубли объединять только при одинаковом намерении, с релевантным 301. Материал без полезного содержания и без подходящей замены можно удалить с 404/410 после проверки ссылок. Непопадание в индекс само по себе не критерий удаления.

Добавить исполняемые мини-проекты к самым востребованным урокам. Обновлять дату только при изменении содержания, а не для имитации свежести.
