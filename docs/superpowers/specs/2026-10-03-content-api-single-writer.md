# Content API как единственный писатель: решения этапа 1

Дата: 3 октября 2026
План: `docs/superpowers/plans/2026-10-03-api-only-migration.md`
Ранбук: `docs/runbooks/api-only-agent-prompts.md`, промпты 1.1–1.10

Документ пополняется по мере прохождения промптов этапа 1. Здесь записаны решения, которых нет в плане, и отклонения от него.

## Схема данных (миграция A, `drizzle/0008_article_versions_build_pointer.sql`)

Только добавления. Старый путь публикации (файлы, админка, `publish.one`) миграция не затрагивает.

### `content_article_versions`

`(article_id, version)` первичный ключ, `document jsonb`, `actor_key_id`, `actor_user_id`, `created_at`.

- `article_id` с `ON DELETE CASCADE`: удаление черновика (промпт 1.5) убирает и его историю. Статью, которая выходила в публичный доступ (`firstPublishedAt` задан, в том числе снятую), удалить нельзя (`was_published`), так что каскад не теряет историю опубликованного.
- Решено в 1.5: `content_publications.article_id` остаётся `ON DELETE RESTRICT` (0007), поэтому `deleteDraft` сначала удаляет публикации статьи в той же транзакции, версии уходят каскадом (см. «`DELETE`» ниже).
- `actor_key_id` и `actor_user_id` с `ON DELETE SET NULL`: отзыв ключа или удаление пользователя не должны блокироваться историей.
- Backfill: одна строка на статью **под её текущим номером версии**, а не под номером 1, как записано в плане. Статья про Mailu на проде уже на версии 3; строка «версия 1» с документом версии 3 была бы ложью, а следующая запись `version + 1` оставила бы дыру. Более ранние документы нигде не хранились, восстановить их нельзя.

### `content_articles`

- `build_publication_id` (FK на `content_publications`, `ON DELETE SET NULL`): желаемое состояние для сборки. Backfill: последняя публикация статьи в состоянии `published`; у черновиков `NULL`.
- `last_modified_at`: `NOT NULL DEFAULT now()`, backfill из `updated_at`. Отдельно от `updated_at`, потому что `updated_at` меняется и от служебных записей.
- `source_version`: для EN, с какой версии RU сделан перевод.
- `unpublished_at`, `manually_edited` (`NOT NULL DEFAULT false`).

### `content_publications`

- `kind` (`publish` | `unpublish`, `CHECK`), `batch_id` с индексом, `dispatched_at`, `hooks_done_at`.
- Backfill `hooks_done_at = updated_at` для публикаций в состояниях `published` и `failed`. Без него воркер из промпта 1.7 отправил бы IndexNow и создал соцчерновики для всех исторических публикаций: условие хуков «`hooks_done_at IS NULL`». Активные публикации (`queued`, `publishing`) остаются с `NULL` и получат хуки после завершения.

### Системный ключ `admin-session`

Строка в `content_api_keys` с `token_hash = 'session:' + 64 нуля`. Хеш настоящего токена это 64 hex-символа sha256, поэтому совпасть с этой строкой он не может. Имя и хеш экспортируются из `src/lib/db/schema.ts` (`ADMIN_SESSION_KEY_NAME`, `ADMIN_SESSION_TOKEN_HASH`). Скоупы в строке определяют права сессии: principal берёт их из строки (промпт 1.2), а воркер проверяет `revoked_at` и `articles:publish` по той же строке. Поэтому правка или отзыв строки действуют одинаково на API и на воркер.

### Что уходит в миграции B (после cutover)

`post_revisions` с триггером `prune_post_revisions` (0002) и `content_guard_manual_revision` (0007), `media_assets`, колонки `base_manual_revision_id`, `base_remote_hash`, `commit_sha`.

### Порядок выкладки

Backfill версий и `hooks_done_at` выполняется один раз, в момент миграции. Если 0008 попадёт на прод раньше кода промптов 1.2–1.7, сохранения в этом промежутке останутся без строк версий, а публикации, завершившиеся в нём, сохранят `hooks_done_at = NULL` и получат хуки с опозданием. Этап 1 выкладывается одним PR.

Строку `admin-session` код ищет по `ADMIN_SESSION_TOKEN_HASH`, а не по имени.

### Снапшоты drizzle

`pnpm exec drizzle-kit check` перед генерацией: «Everything's fine». Сгенерированный SQL содержит только изменения этого шага; отсутствующий `0002_snapshot.json` ложного diff не дал.

## Principal и маршруты (промпт 1.2)

- **Principal.** `authorize(request, locals, scope)` в `src/lib/content-api/auth.ts`. Любой непустой `Authorization` идёт прежним путём Bearer (401, 403, 429) и никогда не падает на cookie; тот же предикат `hasAuthorizationHeader` использует `requiresAuthContext`. Без заголовка берётся `locals.user`: нет пользователя 401, роль не `admin` 403, на не-GET проверка Origin, затем строка `admin-session`.
- **Строка `admin-session` ищется на каждый запрос** по `ADMIN_SESSION_TOKEN_HASH`, без кеша: id меняется, когда таблицу пересоздают (тесты). Скоупы principal берутся из строки. Строка отсутствует или отозвана: `logger.error` и 503 `admin_session_key_missing`, чтобы не принять сохранение с публикацией, которую воркер потом отклонит как `key_revoked`. Лимит 60/мин для сессии не применяется и счётчик строки не меняется.
- **Origin.** `src/lib/content-api/origin.ts`, чистая `allowedOrigins(env)`, считается на каждый вызов. Продакшн (`NODE_ENV=production`): только `CANONICAL_ORIGIN`. Иначе ещё origin из `BETTER_AUTH_URL ?? SITE_URL` (там выдан cookie). Нет ни одной переменной: остаётся только канонический origin, без исключения. Нет заголовка или `null`: 403 `origin_mismatch`. Проверка не заменяет `checkOrigin` Astro, а добавляется к нему.
- **Идемпотентность сессии.** В `content_api_requests.idempotency_key` пишется `${userId}:${key}` (колонка text, схема не меняется), потому что у всех админов один `key_id`. Для Bearer ключ не меняется.
- **Таблица маршрутов.** `src/lib/content-api/routes.ts`: `matchRoute` (чистая; `:id` один непустой сегмент; побеждает первый в порядке массива, поэтому `articles/validate` стоит перед `articles/:id`), `createDispatcher(routes)` (authorize, затем `sessionOnly`, затем handler), `once` для идемпотентных. Ключ `Idempotency-Key` читается лениво внутри `once`: плохое тело по-прежнему получает 415/422 раньше, чем 400 за отсутствующий ключ. В дайджест запроса идёт `params.path` как есть (без нормализации): на проде уже лежат дайджесты по этой строке. Публичные маршруты (`scope: null`) принципала не получают. Запись `openapi.json` в таблице недостижима на сервере (Astro отдаёт `openapi.json.ts` раньше), оставлена для вызова `ALL` напрямую.
- **Единственное намеренное изменение поведения** для существующих маршрутов: у `articles/:id` (GET, PUT), `articles/:id/publish` и `publications/:id` теперь сначала проверяются аутентификация и скоуп, потом формат id. Было 422 на неверный uuid до любой проверки; стало 401 без учётных данных и 403 без нужного скоупа. Запрос с валидным ключом и плохим uuid теперь считается в лимите 60/мин. Разбор uuid остаётся в handler, до разбора тела.
- **`/keys/*`** (промпт 1.5) помечаются `sessionOnly`: Bearer получает 403 `key_cannot_manage_keys`. До этого проверено на синтетическом маршруте в `tests/integration/content-api-session.test.ts`. Промпт 1.5 обязан скрыть строку `admin-session` из списков и запретить её отзыв.
- **Роли.** Доступ по сессии только для `admin`, как в ранбуке. `/admin` guard (`src/middleware.ts`) и `assertAdmin` (`src/actions/_auth.ts`) сегодня пускают и `editor`. Пересмотреть до этапа 3, когда админка переедет на API: иначе editor потеряет возможности.
- **Автор версии.** `authorize` отдаёт `principal.userId`; промпт, который начнёт писать `content_article_versions`, должен передавать его как `actor_user_id`. Сейчас записи делает `keyId = admin-session` без пользователя.
- **Пропущено из ревью (nit):** отдельный тест на запись `openapi.json` в таблице (недостижима на сервере).

## Чтение (промпт 1.3)

- **Статус** считает одна чистая функция `articleStatus` (`src/lib/content-api/status.ts`, без импорта БД; её же возьмёт `articleView` в 1.5). Приоритет: последняя публикация `queued|publishing` (включая unpublish) `publishing`; `failed`; `unpublished_at`; `publishedVersion` пуст `draft`; `version > publishedVersion` `changed`; иначе `published`. Достаточно последней публикации: `content_publications_one_active_idx` и `requireIdle` не дают активной публикации быть не последней. Единственный тип `ArticleStatus` выводится из `articleStatusSchema`. Условие 1.5: при повторной публикации сбрасывать `unpublished_at`, иначе статус останется `unpublished`.
- **Фильтр `status` (вариант A).** SQL фильтрует всё, кроме статуса, и считает порядок и курсор; статус считается и фильтруется в TS по лёгким колонкам (`document->>'title'`, `->'tags'`, `->'provenance'->>'agent'`, тело документа не читается). Без `status` лимит применяется в SQL (`LIMIT limit+1`), с `status` читаются все строки после курсора: O(N) на запрос, нормально примерно до нескольких тысяч статей. Отвергнуто: `CASE` в SQL (правило окажется в двух местах), дочитывание батчей (сложнее без выигрыша).
- **Курсоры.** Base64url JSON `{at, id}`. Статьи: `(updated_at, id) desc`. Публикации и медиа: `(created_at, id) desc`, а не `updated_at`, как в ранбуке: у `content_assets` нет `updated_at`, а `updated_at` публикации меняется, пока клиент листает. Это отклонение от ранбука. `at` строится в Postgres через `to_char(col at time zone 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.US"Z"')` и сравнивается как `(col, id) < (at::timestamptz, id::uuid)`: JS `Date` держит миллисекунды, курсор с округлённым вниз временем при убывающем порядке пропускает строки того же миллисекундного окна за границей страницы (проверено мутацией: тест падает). Курсор валидирует `cursorSchema`: плохой base64 или JSON, `at` вне формата или невозможная дата (круговой разбор через `Date`), не-uuid `id` дают `ZodError` и 422, а не 503 из Postgres. Индекса `(updated_at, id)` нет сознательно. Правка статьи при обходе переносит её в начало: её можно пропустить, это задокументировано.
- **`kind` публикации** есть только в списке `GET /publications/` (`publicationListItemSchema = publicationSchema.extend({kind})`). `publicationView` и ответы создания, обновления и `GET publications/:id` не менялись (тип параметра только сужен до нужных полей, чтобы список не читал `content`), а сохранённые идемпотентные ответы `kind` не содержат: обязательное `kind` в общей схеме сделало бы контракт ложным. Компонент `Publication` в OpenAPI теперь строится из `publicationSchema` (нестрогий вариант, чтобы `allOf` с `url` в `PublicationStatus` оставался валидным), ручное определение удалено.
- **Схемы ответов строгие** (`z.strictObject`): колонка, добавленная в таблицу, не просочится в ответ, а `parse` в тестах умеет падать на утечке (`content` публикации, `hash`/`objectKey`/`keyId` ассета, `searchVector`).
- **Версии.** `document` в ответах это `Record<string, unknown>`: история отдаётся «как сохранено» и не проверяется заново по сегодняшнему контракту записи. `actorKeyId` и `actorUserId` отдаются как есть: это не секреты, а читать может только владелец сайта или его агент; скрыть их можно позже без потери совместимости. Пока 1.5 не пишет версии, отдаётся то, что есть (backfill миграции): список может иметь дыры, а `/versions/{current}` для статьи, сохранённой после миграции, даёт 404 с `details.currentVersion`. Версию не синтезируем: этап выкатывается одним PR.
- **by-slug.** `translation` = null, если нет одной из сторон; иначе `stale = en.sourceVersion === null || en.sourceVersion < ru.version`. Сейчас у всех EN `source_version = NULL`, значит `stale: true`, а `sourceVersion: null` объясняет причину. Покрыты только статьи из `content_articles`: файловый пост даёт 404, хотя создание вернёт `409 slug_conflict`; 404 не значит «slug свободен» (записано в `docs/content-api.md`).
- **Скоупы.** `GET /media/` требует `articles:read`, не `media:write`: список это чтение, агенту нужны `assetId` для ссылок на картинки, URL ассетов и так публичны, а ключ только для чтения не должен получать право загрузки. Новый скоуп не нужен, миграция 0008 не менялась.
- **Маршруты.** `articles/by-slug/:slug` стоит в таблице раньше `articles/:id/versions` (оба три сегмента, побеждает первый). `n` версии: `/^[1-9]\d{0,8}$/`, иначе 422. Query читается из `new URL(request.url).searchParams`, `Object.fromEntries` (при повторе параметра побеждает последний).
- **Пропущено из ревью:** ничего из critical и important; из nit не принято только скрытие `actorUserId` (обоснование выше).

## Удаление конфликтной машинерии (промпт 1.4)

Из Content API убрано всё, что сверялось с `post_revisions` и `base_remote_hash`: `latestManualRevision`, проверки `manual_edit_conflict` (создание, обновление, публикация, воркер), `remote_edit_conflict`, поля `acknowledgedManualRevisionId` и `expectedRemoteHash` в PUT, поля `manualRevision`, `manualEditsPending`, `remote` в GET `articles/:id`. `GET` теперь отвечает `{...articleView, publication}` и не ходит в GitHub.

- **Воркер перезаписывает файл статьи, которой владеет.** `commitArticle(path, content, {overwrite})` по-прежнему читает файл на родительском коммите, обновляет ветку без force и повторяет при 409/422 (до 3 попыток), но не сравнивает файл с сохранённым хешем. Сценарий Mailu (prettier переформатировал файл после публикации) проходит. Совпадение содержимого остаётся восстановлением после потерянного ответа; MDX по тому же адресу остаётся `slug_conflict`.
- **Защита от перезаписи старого поста (TODO(cutover)).** Простой вариант «всегда перезаписывать» оставлял дыру без срока давности: файловый пост с тем же slug мог появиться уже после создания черновика API (`posts.upsert` не смотрит в `content_articles`, а триггер срабатывает только при активной публикации), и воркер молча затёр бы его. Раньше от этого защищали `manual_edit_conflict` и `remote_edit_conflict`. Поэтому воркер считает статью владельцем файла, если `publishedVersion` не пуст или у неё уже есть публикация с `commit_sha`, и передаёт `overwrite: true`. Владение также подтверждается маркером: файл с `apiRevision`, равным id любой публикации этой статьи, перезаписывается (коммит принят GitHub, ответ потерян на последней попытке, `commit_sha` не записан). Первый коммит поверх существующего чужого файла: 409 `slug_conflict`, публикация `failed`. Хеш не хранится. Дополнительно остаётся проверка `existsSync` в `createArticle` (`slug_conflict` при создании). Обе проверки помечены `TODO(cutover)` и уходят с `commitArticle` в этапе 2 / промпте 3.6; правило «slug занят только по БД» начнёт выполняться при cutover. Отвергнуто: вариант без `overwrite` (дыра выше) и «окно между коммитом в `main` и образом» как единственное описание риска: окна без срока остаются, пока файловые посты живы.
- **`relatedSlugs`.** Для каждого slug: если строка в `content_articles` есть (тот же язык), решает она (`publishedVersion !== null`); файл на диске смотрится только при отсутствии строки (`isPublishedPostFile`, `TODO(cutover)`, удаляется в 3.6). Намеренно строже прежнего правила: строка без `publishedVersion` скрывает опубликованный файл с тем же slug, а статья API с живым коммитом, но публикацией в `publishing`/`sitemap_pending`/`failed` (`deployment_timeout`) не принимается как связанная, пока не станет `published`. Совпадение с собственным slug по-прежнему 422 `invalid_related_article`. Открыто для 1.5: должен ли slug статьи с `unpublished_at` проходить проверку.
- **Колонки `base_remote_hash` (в `content_articles` и `content_publications`) и `base_manual_revision_id` не читаются и не пишутся**: у `base_manual_revision_id` остаётся default 0, `base_remote_hash` остаётся `NULL`. Они удаляются миграцией B. Миграции в этом промпте нет.
- **Триггер `content_guard_manual_revision` (0007) остаётся**, потому что админка ещё пишет `post_revisions`; уходит в миграции B вместе с таблицей.
- **Известные ограничения до cutover.** API больше не читает `post_revisions`. Правка файла статьи API в админке вне активной публикации будет молча перезаписана следующей публикацией через API; правка останется только в истории git. Во время публикации триггер блокирует сохранение. В обратную сторону: `publish.one` коммитит файл с диска контейнера, если он отличается от remote, поэтому до следующей выкладки публикация из админки может откатить коммит API устаревшим содержимым.
- **`path_conflict` и `branch_busy` остаются в `github.ts`** до этапа 2 (отклонение от буквы ранбука): от `base_remote_hash` они не зависят и уйдут вместе с `commitArticle`. `branch_busy` недостижим (на 3-й попытке выбрасывается исходная ошибка); `throw` после цикла нужен только ради типа возвращаемого значения. `readRemoteArticle` остался без вызывающих и удаляется вместе с `commitArticle`.
- **Контракт.** `updateArticleSchema` строгий: `acknowledgedManualRevisionId` и `expectedRemoteHash` дают 422, принимать и игнорировать их не стали (клиент один, агент владельца). Описано в `docs/content-api.md` как ломающее изменение. `docs/api/openapi.json` перегенерирован.
- **Идемпотентность.** Сохранённые ответы `content_api_requests` со старой формой не мигрируются, повтор отдаёт их как есть. Сохранённые дайджесты PUT содержат `acknowledgedManualRevisionId: 0` (default попадал в разобранный ввод): сетевой повтор PUT, отправленного до выкладки, получит `409 idempotency_conflict`, а не сохранённый ответ. Это приемлемо.
- **Порядок проверок `updateArticle`:** версия, `requireIdle`, неизменяемость идентификаторов, `validateDocument`, update.
- **Тесты.** Гонка двух PUT с одним `expectedVersion` даёт ровно один 409 `version_conflict` (проверено мутацией: без advisory lock в `mutateOnce` тест падает). Воркер: первый коммит поверх чужого файла `failed`/`slug_conflict`, повтор после коммита и ветка `publishedVersion` перезаписывают переформатированный файл (мутации обеих половин `overwrite` роняют тесты). Переформатирование файла проверяется на уровне `github.ts` (unit), а не в моке интеграционного теста.

## Запись, часть 1 (промпт 1.5: версии, restore, delete, unpublish, batch)

Пункты 1-5 и 9 ранбука. Пункты 6-8 и 10 (posts-meta, `/keys`, упрощение контракта, `searchVector` по языкам) в следующем проходе; ничего в этом проходе их не блокирует (`writeVersion` и `Actor` готовы для перевода из 1.6).

- **Actor.** `actorOf(principal)` даёт `{keyId, userId | null}`; сервисные функции берут `Actor`, а не `keyId`. Единая точка записи версии: `writeVersion(tx, current, document, actor)` (update, restore, позже translate), `createArticle` пишет версию 1 тем же `recordVersion`.
- **`status` в `articleView(article, latest)`.** `requireIdle` теперь возвращает последнюю публикацию (по `createdAt desc, id desc`), так что N+1 нет. Если операция создала задание, в `articleView` передаётся оно (иначе в 202 было бы прошлое состояние, а не `publishing`). `state` не менялся и объявлен устаревшим.
- **Время.** Строки `unpublish` получают `createdAt` из часов приложения, как `enqueuePublication`: «последняя публикация» сравнивает оба вида строк, а часы БД и приложения расходятся (пойман интеграционным тестом).
- **Unpublish: вариант B.** `unpublished_at = now`, `published_version = NULL`, `published_content = NULL`, `build_publication_id = NULL`, `first_published_at` остаётся (при повторной публикации сохраняется `pubDate`). Отвергнут вариант A (только `unpublished_at`): `relatedSlugs` принимал бы снятую статью, `DELETE` вечно отвечал бы `unpublish_first`, а `publishedContent` лгал бы. Успешная **публикация** сбрасывает `unpublished_at` в воркере, а не при постановке в очередь. Снятие работает **по языку** (в отличие от админского удаления, которое убирает оба файла и `posts_meta`): оба языка = два вызова; `posts_meta` общая для RU и EN и остаётся ради order/pinned. Лишняя строка ничего не показывает: поиск и списки сверяются с коллекцией (`pagefind-node.ts`).
- **Владение файлом.** `ownsCommittedFile(publications)` (чистая функция в `status.ts`): побеждает самое свежее из двух событий, `publish` с `commit_sha` или завершённый `unpublish`; победа `publish` значит «файл в git». Воркер считает владельцем `publishedVersion !== null || ownsCommittedFile`, а `ownedRevisions` берёт только из `kind = 'publish'` (закрыт `TODO(cutover)` про 1.5). Убрать при cutover вместе с `commitArticle`.
- **Воркер, unpublish.** `deleteArticle` в `github.ts` рядом с `commitArticle` (общие хелперы чтения на parent, без force, 3 попытки на 409/422, MDX даёт `slug_conflict`; нет файла: возвращает parent как восстановление; чужой файл: `slug_conflict`). Проверка `verifyUnpublished`: страница 404/410 и настоящий sitemap (`<urlset` и хотя бы один `<loc>`) без адреса. «Ещё не готово» это ожидание (`nextAttemptAt`, без исключения), а не ошибка: иначе счётчик попыток провалил бы задание за ~4 минуты вместо 30. Срок 30 минут от входа в `publishing`, затем `504 deployment_timeout`. По завершении `hooks_done_at = now`, чтобы раннер хуков из 1.7 (условие `hooks_done_at IS NULL`) не рассылал IndexNow и соцчерновики о снятии. `publicationView` получил `kind` (необязательное поле схем: сохранённые ответы его не содержат).
- **Publish после снятия.** `POST /publish/` и элемент пакета отвечают `unchanged`, только если последняя публикация не `unpublish`: неудавшееся снятие, чей коммит прошёл, иначе навсегда оставило бы сайт без страницы при `publishedVersion` на месте. В пакете `requireIdle` вызывается и для unchanged-элементов.
- **`DELETE`.** Формат `If-Match: "<version>"` (строгий ETag из GET; `ifMatchVersion` в `http.ts`): нет заголовка `428`, не та форма `400 invalid_if_match`, не совпало `412`. Порядок: 404, 412, `publication_in_progress`, `unpublish_first` (опубликована или файл в git по `ownsCommittedFile`), `was_published` (`firstPublishedAt` задан; решение: история вышедшего в публику не удаляется, так что инвариант выше сохранён). Публикации статьи удаляются первыми (FK `RESTRICT`), версии каскадом. Ответ `200 {id, deleted: true}`: `jsonResponse` с телом и статусом 204 бросает. Путь для черновика с «застрявшим» файлом: `unpublish`, затем `DELETE` (завершённый `unpublish` снимает признак владения, `firstPublishedAt` остаётся пустым).
- **`referenced_by_related`.** `relatedSlugs` пишутся в закоммиченный Markdown жёсткими ссылками, а `validateDocument` страхует только новые сохранения. Поэтому `unpublish` отказывает (`409`, `details.articleIds`), пока опубликованная статья того же языка перечисляет slug в `relatedSlugs`. Сверка по `publishedContent` (закоммиченный Markdown: ссылку убивает живая версия, а не черновик; ссылка ищется как `(/blog/<slug>/)` или `(/en/blog/<slug>/)`), не по `document`. Отвергнуто: возвращать предупреждение (битая внутренняя ссылка не ловится ни одной проверкой сборки).
- **Batch.** До двух элементов, один slug (разные id при уникальном `(slug, lang)` значат разные языки), общий `batch_id`, вся операция в одной транзакции `once`. RU идёт первым: `createdAt` задаётся явно, на 1 мс позже у следующего.
- **Остаточные риски.** Гонка: статья Y может опубликоваться со ссылкой на X, пока снятие X в очереди (`validateDocument` видит `publishedVersion` X), и после снятия X ссылка Y умрёт; воркер ссылки повторно не сверяет. Коммит, принятый GitHub, но с потерянным ответом (`commit_sha` NULL): `DELETE` его не замечает, и файл может осиротеть (до cutover). `last_modified_at` при сохранении не обновляется (решить в 1.6 или этапе 2). После `DELETE` строка `posts_meta`, созданная неудачной попыткой, остаётся и безвредна.
