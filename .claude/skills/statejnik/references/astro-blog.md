# Привязка к репозиторию

Источник: предоставленный владельцем пакет `statejnik-1.1.0/statejnik`.
`references/editorial-standard-upstream.md` и пять Python-файлов в `tools/`
перенесены без изменений. Исходный README ссылается на LICENSE.md, но в полученном
пакете этого файла нет; сведения о лицензии не добавлялись от себя.
Остальные инструкции адаптированы для artka.dev.

## Принятые редакционные решения

Практический прогон — расширение статьи `mermaid-svg-playwright-build-time`,
опубликованное через PR #65. Его результат — пример, а не шаблон на все темы.

| Исходная методика             | Правило проекта                                                              |
| ----------------------------- | ---------------------------------------------------------------------------- |
| Автономно до публикации       | Сначала драфт и сравнение; публикация по явному запросу                      |
| Нет квоты слов                | Для полной статьи по умолчанию 1500–2000 слов без кода; прямой запрос важнее |
| Только новая SEO-статья       | Новая статья, рерайт, расширение и учебный материал                          |
| Ежедневный подбор тем         | Только по отдельному запросу                                                 |
| Оффер и обязательный CTA      | Полезный следующий шаг читателя без придуманной продажи                      |
| Семь QA-ролей и CMS-квитанции | Автор, редактор, проверяющий; реальные артефакты и SHA-256                   |
| AI-score как блокер           | Сигнал для редактора с разбором ложных срабатываний                          |

Голос: инженер объясняет инженеру. Термины раскрываются по необходимости;
нет выдуманных кейсов, личного опыта, обещаний трафика и фамильярности.
Нормальная русская пунктуация допустима. Код, URL, точные цитаты и технические
условия не меняются ради стилистических метрик.

## Формат и версии

- Схемы и ограничения: `src/content.config.ts`, `src/lib/content/limits.ts`;
  курсы и уроки — `src/lib/courses/schema.ts`. Читай актуальные файлы, не копируй
  номера версий или лимиты из старого задания.
- У поста H1 создаётся из `title`; второй H1 в теле не нужен. Драфт поста:
  `draft: true`, `lang: ru`. У уроков другой набор полей, включая `locale`;
  не добавляй поля поста механически. Все рабочие драфты остаются вне коллекций.
- Для рерайта сохраняй путь, slug/URL и `pubDate`; `updatedDate` отражает реальную
  проверку. Служебные brief, claims и отчёты не входят в текст статьи.
- Держи исходник и показанные версии неизменными. Сравнение должно показывать
  полный текст и количество слов, а не только список улучшений. Для новой статьи
  исходника нет: достаточно полного превью с версиями последующих доработок.
- Исходный `new-blog-post` — дополнительный справочник формата. Его обязательные
  FAQ/диаграммы, отдельное согласование плана и `draft: false` не перекрывают
  текущий запрос пользователя и контракт Statejnik.

## Публикация

Этот раздел применяется после явного запроса на выпуск. Разрешение в текущей
беседе уже достаточно; дополнительное согласование того же действия не нужно.
Переноси именно показанную и одобренную версию. Техническая смена `draft`,
локализация и актуализация метаданных допустимы; если требуется существенно
переписать смысл после одобрения, сначала покажи изменённый драфт пользователю.

1. Сверь diff с одобренным файлом и его хешем. При рерайте замени существующую
   статью на прежнем пути, при новой публикации проверь свободный slug.
   Для Git-публикации поста выстави `draft: false`.
2. Следуй текущему разделу i18n в `CLAUDE.md`: обнови EN-двойник и проверь
   `pnpm translate:check`. Если автоматический перевод недоступен, сообщи причину;
   ручной перевод пометь `manuallyEdited: true` и запиши SHA-256 окончательного
   RU-файла в `sourceHash`. Не обходи проверку рассинхронизации. Для курсов
   используй их отдельный порядок локализации, а не переводчик постов.
3. Определи актуальный путь публикации по репозиторию. Для существующей файловой
   статьи используй Git; не создавай её дубль в CMS. Выполни положенные проверки
   и хуки, включи в коммит только нужный контент и перевод. Локальные эксперименты
   и скриншоты не добавляй автоматически. GitNexus `detect_changes` обязателен
   перед коммитом; impact — перед изменением существующих функций приложения.
4. После выпуска проверь живые RU/EN URL, HTTP 200, соответствие текста принятой
   версии, canonical/hreflang, отсутствие непреднамеренного noindex и sitemap.
   Успешный CI или отправленный webhook ещё не подтверждают публикацию.
   Если сервер предоставляет версию коммита, сверь её с релизом.

Не запускай уведомления, индексационные API, рассылки или расписания только
потому, что они описаны в исходном пакете. Они требуют отдельного запроса.
