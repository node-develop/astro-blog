У статьи есть автор, сайт и собственный адрес. Если эти сведения формируются в разных компонентах, легко получить двух «авторов» с разными URL или дату обновления, которая не совпадает с видимой страницей. Единый JSON-LD-граф удобен прежде всего тем, что такие расхождения легче заметить.

Сам по себе `@graph` не гарантирует индексацию, расширенный сниппет или цитирование AI-сервисом. Несколько корректных JSON-LD-блоков тоже допустимы. Выбор одного графа здесь — решение о сопровождении кода.

## Как это устроено в репозитории

На artka.dev сведения об авторе и сайте вынесены в общий слой — каталог `src/lib/seo`. Страница добавляет собственные сущности и ссылается на общие через стабильные `@id`. Это позволяет менять профиль автора в одном месте. Исходный код сайта не опубликован, поэтому ниже только сокращённые фрагменты; мой профиль на GitHub — [node-develop](https://github.com/node-develop).

Сокращённый пример связей, а не полный шаблон Google Article:

```json
{
  "@context": "https://schema.org",
  "@graph": [
    {
      "@type": "Person",
      "@id": "https://artka.dev/#person",
      "name": "Artyom Kashuta"
    },
    {
      "@type": "WebSite",
      "@id": "https://artka.dev/#website",
      "url": "https://artka.dev/",
      "name": "artka.dev"
    },
    {
      "@type": "WebPage",
      "@id": "https://artka.dev/blog/json-ld-graph-astro/#webpage",
      "url": "https://artka.dev/blog/json-ld-graph-astro/",
      "isPartOf": { "@id": "https://artka.dev/#website" }
    },
    {
      "@type": "BlogPosting",
      "@id": "https://artka.dev/blog/json-ld-graph-astro/#article",
      "headline": "JSON-LD @graph в Astro",
      "author": { "@id": "https://artka.dev/#person" },
      "mainEntityOfPage": {
        "@id": "https://artka.dev/blog/json-ld-graph-astro/#webpage"
      }
    }
  ]
}
```

Ключевой инвариант: адрес страницы в графе, canonical, sitemap и внутренних ссылках должен обозначать одну и ту же версию URL. На этом сайте используется завершающий слеш. Английская статья имеет собственный `/en/`-адрес; язык связывается через hreflang, а не подменяется canonical на русский оригинал.

## Что проверить перед публикацией

Данные нужно брать из той же записи контента, из которой строится видимая статья. Иначе редактор исправит заголовок, а JSON-LD продолжит отдавать старый.

Проверьте:

- `headline` соответствует опубликованному заголовку;
- `datePublished` сохраняет исходную дату, `dateModified` меняется после содержательного обновления;
- изображение доступно по абсолютному URL и действительно относится к странице;
- имя автора и профиль не расходятся между языками;
- ссылки через `@id` указывают на нужные сущности;
- в разметку не попали секреты, черновики или текст, которого нет на странице.

Для вставки JSON внутрь HTML нужен сериализатор, который не позволяет строке `</script>` завершить элемент раньше времени. В репозитории для этого используется `safeJsonLd`. Самодельная конкатенация строк с frontmatter в `set:html` здесь не подходит.

## Проверяйте ответ сервера

Откройте исходный HTML опубликованной страницы и найдите `application/ld+json`. Разберите содержимое JSON-парсером. Затем проверьте граф в Schema Markup Validator и поддерживаемые Google типы в Rich Results Test. Валидный JSON, корректная Schema.org-разметка и право на конкретный поисковый формат — три разные проверки.

В этом проекте есть `pnpm verify:seo-build`; его следует запускать после `pnpm build`. Локальная проверка полезна до выпуска, а запрос к production ловит проблемы адресов, редиректов и доступа к изображениям, которые локальная сборка не видит.

## Где заканчиваются возможности разметки

[Google описывает](https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data) структурированные данные как способ объяснить содержимое и получить право на поддерживаемые формы представления; показ не гарантируется. Разметка не компенсирует неверный текст.

Отдельное исправление прежней версии: FAQ rich results перестали показываться в Google 7 мая 2026 года, что отражено в [журнале изменений](https://developers.google.com/search/updates). Полезный раздел вопросов можно оставить читателям, но обещать за него поисковый бонус нельзя.

Следующий уровень проверки — доступность самой страницы. Это разобрано в [статье про robots.txt и индексацию](/blog/robots-txt-ai-crawlers-2026/).
